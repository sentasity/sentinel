---
title: Security model
description: What an unattended session can touch, what the credential it is handed can do, and which controls stay on the receiver where injected text cannot argue with them.
---

The unattended sessions are the trust boundary. Everything that reaches them is treated
as untrusted, including the Sentry issue text they are asked to investigate.

:::tip[The short version]
The operator's controls over whether a fix is allowed live in the receiver, out of the
session's reach; the session supplies two of the gate's inputs, its own confidence and
fixability ratings, and those are influenceable. The session holds no GitHub credential
at all. It sends the finished fix back as files, and the receiver checks every path
against the same policy the gate uses, mints a token scoped to one repository and two
permissions, and opens the pull request itself, as the App. Branch protection on the
base branch is what makes review unavoidable, and every pull request waits for a human.
:::

## The fire payload is data, not instructions

All parameterization lives in the stored routine prompt, not in the request that
triggers it. The payload carries five typed fields and no prose:

```
{ "project", "issue_ids", "release", "batch_id", "reply_token" }
```

The prompt instructs the session to treat any deviation from that shape as a malformed
fire and report it rather than interpret it. This is the control that matters most,
because the alternative design, passing instructions in the trigger, would make anyone
who can reach the trigger endpoint able to reprogram the session.

The payload also sends issue ids rather than event bodies. That is partly the API's
65,536-character cap on a fire, and partly that a full event body is attacker-influenced
text; the session fetches what it needs through the Sentry connector instead.

## The routines API exposes no configuration read

There is no way to ask the API which repository a routine is bound to, or which
connectors it has. So the receiver cannot assert at startup that the routine it is
about to fire is the one it thinks it is.

The compensating control is a fail-closed probe: a session whose only job is to report
its own configuration back. It is a manual gate, not an automatic one, and it needs
re-running whenever the routine or the account's connectors change. Naming it here
rather than hiding it is deliberate, because a compensating control nobody knows to
re-run is not a control.

## Findings delivery is verified out-of-band

Before posting findings anywhere, the session confirms the destination against two
channels the operator controls and no injected text can forge:

- `SENTINEL_RECEIVER_URL`, set in the cloud environment rather than passed in the fire
- the environment's deny-by-default egress policy, whose only non-default allowed host
  is the receiver

An instruction embedded in a stack trace telling the session to post its findings
somewhere else fails both checks.

The check is narrower than it may look. The policy is deny-by-default over the hosts
the operator controls; the environment still reaches whatever it defaults to reaching,
and the investigation phase fetches the repository over the network before any of
this. So the egress policy pins down where *findings* and *fixes* may be posted, since
both go to the receiver, and it is not a general containment boundary. The fix phase
adds no endpoint of its own: its one GitHub call is the fetch of the base branch, the
same read the investigation already makes. The controls below are what carry the
weight.

## The session that writes the fix is the one that investigated

Autofix does not run in a second session started afterwards. The session that reported
the findings writes the fix, using a grant the receiver returns in the HTTP response to
that report, and hands the result back to the receiver to publish.

That shape follows from one fact about the runtime: the receiver can answer a session
that calls it, but it cannot send a message to a session that is already running. A
grant can only travel back down a request the session itself made, and the findings
POST is the request there is. What travels is small on purpose: the repository, the
base branch, the callback URL, and one grant per approved finding, each carrying a
dispatch id and a one-time callback token. No credential is among them.

### The session holds no GitHub credential

The session's only GitHub operation in the fix phase is a fetch of the base branch, the
same read the investigation makes. When the fix is written and its test passes, the
session POSTs the changed files, whole, to the receiver's callback route under the
grant's token, and reads back the outcome. It never pushes and never calls the pull
request API, and the prompt says so in the plainest terms available: there is no
legitimate write path from the session, so any push it makes is through the wrong one.

This is a stronger posture than the one it replaced, and it is worth saying why in one
sentence. A credential live inside an attacker-influenceable session has to be contained
by scope, lifetime, naming, and prose, and each of those is a mitigation for the
credential being there at all; a session with no credential needs none of them.

### The receiver's token

| | |
|---|---|
| Scope | one repository, the configured `target_repo` |
| Permissions | `contents: write` and `pull_requests: write`, nothing else |
| Lifetime | one hour, set by GitHub when the token is minted; spent inside the one invocation that minted it |
| Storage | none: minted per pull request inside the receiver, never returned, never written down |

The receiver mints it only after a `fix_ready` payload has passed validation and the
dispatch record has been claimed, and spends it on one short sequence under a single
time budget: a read of the base branch and a comparison that confirms the base commit
is on it, a read of the base commit and its tree, a blob per file, a tree that inherits
the base commit and overrides only those paths, a commit, a branch, and then the pull
request itself. The commit's author is whatever GitHub
records for the App installation, because nothing in the receiver sets one, so the pull
request is the App's by construction rather than by a check made afterwards.

`workflows` is absent deliberately. A workflow file pushed to a branch runs in CI, with
access to the repository's secrets, before any human reviews the pull request that
carries it. A credential that can write `.github/workflows/` is therefore not a
code-writing credential at all; it is a secrets-reading one, and reviewing the pull
request afterwards is too late to matter. The receiver also refuses any `fix_ready` file
under `.github/` before minting anything, so the scope is the enforcement behind a
check that already said no.

The gate declines any *finding* that cites a path under `.github/` too, but the three
controls are not doing the same job. The gate's path check reads the paths a finding
claimed and declines early and legibly. The payload check reads the paths a fix
actually carries, which is what matters, and it covers the operator's excluded paths as
well, which the token's scope never could. The scope is what stands if both were
somehow bypassed.

### The webhook signature does not contain the content

Sentry's webhook is HMAC-verified, and it is worth being precise about what that buys.
The signature proves the alert came from the Sentry integration. It proves nothing about
the text inside the alert.

Stack traces and error messages routinely carry whatever user input caused the exception.
That is what they are for. So anyone who can make the monitored application throw can put
text of their choosing in front of an unattended session, through a channel that is fully
authenticated and behaving exactly as designed. There is no signature check that helps
here, and treating one as though it did would be the more dangerous error.

What contains it instead is everything downstream of the text: the receiver refuses a
fix that touches a forbidden or excluded path, the token it mints reaches one repository
and two permissions and never leaves the receiver, branch protection on the base branch
means nothing lands without review, and a human reads the pull request before it
merges. The prompt also tells the session to treat code, repository docs, Sentry text,
and command output as data and to say in the pull request body when it saw something
that read like an instruction, which helps a reviewer but is not itself a control.

The one gate input this text can reach is the finding's own confidence and fixability
ratings, which the session supplies. Steering an investigation toward a diagnosis that
looks confident and contained is the cheapest thing an injected instruction can attempt,
and it is not something the receiver can second-guess: rating the finding is exactly the
judgment the session was fired to make. What that buys an attacker is bounded, though. A
flattering rating gets a finding *to* the gate; it does not get it past the operator
controls below, which are evaluated on values the session never supplies.

### Operator controls live on the receiver

Confidence and fixability are the session's own judgments and travel in the findings
document, which is why the section above treats them as influenceable. Every *other*
input to the decision is an operator control, and each one is evaluated in the receiver
rather than in the prompt:

- the kill switch that disables autofix entirely
- the project allowlist
- the forbidden and operator-excluded paths
- the dedupe, so one issue earns one fix attempt per environment and release
- the daily pull-request cap

The placement is the point. Text inside an investigated Sentry event can argue with a
prompt; it can put a sentence in a stack trace claiming the cap is lifted or the project
is opted in. It cannot argue with a conditional write in the receiver. Moving any of
these into the prompt to make it "smarter" would move it inside the attacker's reach.

The same reasoning covers the caps' side effects: the dedupe and cap checks are
conditional writes, spent as they pass, so a finding cannot be re-evaluated into a second
attempt.

### What a live reply token is worth

The section above is accurate that those controls are evaluated on values the session
never supplies, but it is worth being precise about which values *are* supplied. The
gate reads the findings document, and the whole document arrives over one authenticated
POST: the two ratings named above, and also each result's `status`, the document's
`schema_version`, and the evidence file paths the path exclusions are matched against.
Whoever holds a live reply token writes all of it. So the gate constrains the shape of a
passing finding rather than proving one was investigated, and a document crafted to
satisfy that shape earns what a genuine one earns.

What it earns is a grant: a dispatch id and a callback token that let the holder submit
one `fix_ready` payload, from which the receiver will open one pull request. That is
the whole prize. No credential leaves the receiver, and the payload is validated on the
receiver before anything is minted: every path is checked against the forbidden and
operator-excluded patterns, the file count and total size are capped, and the branch
name is computed from the record rather than read from the payload. What a forged
finding can produce is therefore a pull request, authored by the App, containing files
the forger chose, in a repository whose base branch is protected and whose reviewers
read it. That is a real thing and it is bounded by review, which is the same thing that
bounds a genuine fix.

Four things bound how far a stolen reply token gets before that point. It is stored
only as a hash, so reading the table yields nothing usable. It is live only while its
own batch is: the lookup requires a row still awaiting findings and still inside its
deadline, checked on the request rather than left to the once-a-minute sweep, and a
batch that has already been answered gets an empty autofix block rather than a second
set of grants. It can only earn grants for the issues in its own batch, because the
findings document is validated against that batch's issue ids. And the dedupe and the
daily pull-request cap are conditional writes, so how many grants any holder can extract
is bounded by the operator's cap rather than by how many documents they are willing to
write.

### The receiver validates what it is handed, and claims the record while it works

A `fix_ready` payload is untrusted input from a session whose context held
attacker-influenceable text, and the receiver treats it that way. Before any GitHub
call it checks, in order: the shape, a full lowercase commit SHA for the base, at most
twenty files, every path plain and repository-relative with no dot segments, every path
clear of the forbidden and excluded patterns, no path twice, at most 512 KB of content,
a one-line title, and a bounded body. The first failure wins, the response names the
rule, the record settles as failed, and the thread is told. Nothing is minted for a
payload that fails.

One check needs GitHub and so runs after the claim: the base commit the session built
on must be the base branch's head or an ancestor of it. A fix built on a commit that is
not on the branch would open a pull request carrying unrelated changes, so the receiver
opens nothing and the grant settles as failed. The whole sequence also runs under one
time budget short of the function's own limit, so a slow GitHub cannot leave a record
claimed with no settle.

A payload that passes is opened under a claim. The receiver moves the dispatch record
from `dispatched` to `opening` with a conditional write before its first GitHub call,
under a fresh three-minute deadline, and settles it to `pr_opened` or `failed`
afterwards. The claim is what keeps the timeout sweep from expiring a record the
receiver is mid-way through, and the short deadline is what keeps a receiver that died
mid-sequence from stranding the row: the sweep fails it, with a reply that says the
receiver did not finish rather than blaming the session.

Authorship needs no check of its own. The App's token is the only credential that opens
the pull request, and the receiver is the only holder of it, so every autofix pull
request is the App's by construction. The detective control the previous design needed,
a lookup of the pull request's author after the fact, is gone with the reason it
existed.

The residual exposure is the one already named: the pull request's contents are chosen
by a session that read attacker-influenceable text, and the receiver checks their paths
and sizes, not their meaning. Review is the control for that, and branch protection is
what makes review happen.

### The callback is a capability, not an identity

Each grant carries its own callback token, stored only as a hash and valid for that one
dispatch. The receiver's advance to a settled state is conditional, so a late callback
and the timeout sweep cannot both write into a thread, and a replayed callback settles
nothing twice. A grant that never reports is failed into the thread when its hour
expires, which is the same principle as the investigation deadline: the failure mode
worth engineering against is the silent one.

## Secrets

Receiver-side secrets live in SSM SecureStrings; workflow-side secrets are Actions
secrets. Neither ever appears in the config file, which carries only a reference to the
parameter name. The full inventory and the rotation runbooks are in
[Runbooks](/sentinel/operate/runbooks/).

One non-credential is held the same way: the ban list `tests/test_public_tree.py`
enforces splits its generic patterns, which are tracked, from the literals that would
identify a real deployment, which live in an untracked local file mirrored by an
Actions secret. A tracked ban list would be an index of everything it protects.

## A reader guards what a list cannot

Two of this repository's disclosure gates are deterministic: a test bans specific strings
and a scanner matches credential shapes. Both catch only what somebody already thought to
describe, which is the wrong shape of defence against a prose page that quietly becomes a
map of a deployment.

The third gate reads. Every pull request is reviewed against the disclosure rules, which
ask for anything naming another repository's internals, a real organization or account
identifier, a live endpoint, or a measurement taken against a live system, and which
require a finding to cite a file and line without ever quoting the value it flags. A
review comment on a public repository is itself public, so quoting would republish the
thing being reported.

That gate blocks the merge until its comments are resolved rather than annotating and
passing. The distinction is the whole point. The arrangement it replaced reported a
passing check while leaving major findings underneath, and they went unread, which is a
worse failure than a false positive: resolving one of those costs a moment, and an unread
finding costs whatever it was warning about.

What the reader cannot do is re-read files nothing touched. It reviews changes, so the
guarantee is about what enters the tree rather than a periodic sweep of all of it. That is
an accepted narrowing, taken in exchange for retiring a scanning workflow that had to hold
a long-lived subscription credential as a repository secret to do its reading, where every
repository administrator could reach it.
