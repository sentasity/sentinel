One issue, three artifacts, in the order they land in a Teams thread.

## 1. The alert

A payment capture times out against the gateway. Sentry raises the issue and webhooks
it to the receiver, which verifies the signature and posts this card.

<AdaptiveCard card={errorCard} />

The gate lets this one through: it is error-level, `staging` is an investigated
environment, and its release resolves to a commit SHA, so the session will read the
code that actually produced the error rather than today's default branch. The issue is
queued with a debounce and picked up by the next sweep.

## 2. The investigation

The session checks the repository out at that SHA, reads the traceback and the
surrounding code, and posts its findings back. The receiver renders them as a reply in
the alert's own thread.

<AdaptiveCard
  card={replyCard}
  caption="Open **Details** for the evidence and assumptions, which Teams collapses the same way."
/>

The finding is that `capture_intent` raises on its polling deadline, but the caller
wraps it in a bare `except` and reports the capture as sent, so the failure never
surfaces. The suggested fix mirrors `refund_intent`, which already has an explicit
timeout branch.

Urgency is **high**. A capture reported as sent when it was not puts payment data at
risk, which would make this urgent in production, but the issue has only been seen in
`staging`, so it is rated one level lower. Urgency says how much the issue matters and
leads the status line so it is the first thing a reader scans.

Confidence is **high** and fixability is **high**. Those two values decide whether the
session goes on to attempt a fix; urgency plays no part in that decision.

## 3. The fix

With `autofix.enabled` on, a finding at high confidence and high fixability clears the
gate, so the receiver answers the findings POST with a grant. The same session then
judges drift against the base branch, re-verifies the root cause, writes the change and
a test for it, and sends the changed files back to the receiver with the base commit and
the pull request text. The receiver opens the pull request as the App and reports the
outcome into the same thread.

Nothing merges automatically. The session never holds a GitHub credential; the receiver
mints one that can write contents and open pull requests in one repository for one hour
and nothing else, spends it, and the pull request waits for a human exactly like any
other.

## Severity variants

The renderer handles four severities. Fatal, error, and warning are investigated. Info
is posted for visibility and says so, unless it is an N+1 performance issue, which is
investigated like an error.
