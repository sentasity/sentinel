One issue, three artifacts, in the order they land in a Teams thread.

## 1. The alert

A payment capture times out against the gateway. Sentry raises the issue and webhooks
it to the receiver, which verifies the signature and posts this card.

<AdaptiveCard
  card={errorCard}
  caption="Rendered from `fixtures/cards/error.json`."
/>

The gate lets this one through: it is error-level, `staging` is an investigated
environment, and its release resolves to a commit SHA, so the session will read the
code that actually produced the error rather than today's default branch. The issue is
queued with a debounce and picked up by the next sweep.

## 2. The investigation

The session checks the repository out at that SHA, reads the traceback and the
surrounding code, and posts its findings back. The receiver renders them as a reply in
the alert's own thread.

<AdaptiveCard
  card={replyCard}
  caption="Rendered from `fixtures/cards/reply.json`. Open **Details** for the evidence and assumptions, which Teams collapses the same way."
/>

The finding is that `capture_intent` raises on its polling deadline, but the caller
wraps it in a bare `except` and reports the capture as sent, so the failure never
surfaces. The suggested fix mirrors `refund_intent`, which already has an explicit
timeout branch.

Confidence is **high** and fixability is **high**. Those two values are the only thing
that decides what happens next.

## 3. The fix

With `autofix.enabled` on, a finding at high confidence and high fixability clears the
gate, so the receiver dispatches the workflow. An unattended session judges drift
against the current default branch, re-verifies the root cause, and writes the change.
A separate publish step then opens the pull request as the GitHub App and reports the
outcome back into the same thread.

Nothing merges automatically. The session that wrote the fix holds no credential that
could push it, and the pull request waits for a human exactly like any other.

## Where this comes from

These are not screenshots, and the conversation around them is not real. Each card
above is the card definition `receiver/cards.py` produces, read from its committed
fixture and drawn here as HTML.

That is a stronger claim than a screenshot, not a weaker one.
`tests/test_card_goldens.py` asserts every one of those fixtures equals what the
renderer produces, on every run, so a change to the renderer that is not reflected in
these files fails the build. The cards on this page cannot drift from what actually
gets posted.

The deployment they describe is fictional. `acme-tools/checkout` is an invented project
carrying an invented bug, so that nothing here reflects a real system.
