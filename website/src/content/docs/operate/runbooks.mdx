Runbooks for the credentials the engine holds, what autofix needs on the GitHub side, and how to read what the pipeline reports about itself. Deploying the receiver itself is covered in [infra/README.md](https://github.com/sentasity/sentinel/blob/main/infra/README.md); the one-time Microsoft and Sentry setup lives in [Microsoft setup](/sentinel/deploy/microsoft/) and [Sentry setup](/sentinel/deploy/sentry/).

## Credential inventory

| Credential | Where it lives | Purpose |
|---|---|---|
| `/sentinel/github-app-private-key` | SSM SecureString, receiver | The autofix App's private key, read by the receiver at cold start; it mints the scoped installation tokens vended to fix sessions |
| `SENTRY_WEBHOOK_SECRET`, `SENTRY_API_TOKEN`, `BOT_CLIENT_SECRET`, `ROUTINE_TRIGGER_TOKEN` | SSM SecureStrings, receiver | Webhook verification, Sentry API access, the bot identity, and the routine fire token |
| Vended installation tokens | Nowhere: minted per batch, returned in the `/findings` response, never stored | Lets the fix session push a branch and open a pull request; scoped to the target repo, `contents: write` and `pull_requests: write`, one hour |
| Callback capability tokens | DynamoDB, hashed, one per dispatch | Bearer credential the fix session presents to `/autofix-result`; scoped to a single dispatch, not reusable |
| `SENTINEL_BANNED_PATTERNS` | Actions secret, engine repo | The deployment-identifying ban patterns `tests/test_public_tree.py` enforces; not a credential, but held like one because publishing the list would index what it protects |

The routine trigger token is never stored in this repo; keep the only other copy in your password manager.

## What the autofix App needs

The receiver mints every autofix credential itself, so the App's configuration is the only thing standing between a passing gate and a pull request:

- The App must be **installed on the target repository**, the one named by `target_repo`. Minting looks that installation up by repository, so an App installed on the organization but not on this repository fails at the lookup.
- The installation must grant **contents: write** and **pull requests: write**. The receiver downscopes each minted token to exactly those two, and a token can never hold a permission the installation lacks, so a missing one produces a token that cannot push or cannot open the pull request.
- Do **not** grant `workflows`. It is excluded from every minted token on purpose ([why](/sentinel/security-model/)), and granting it at the installation widens the App's own reach for no benefit here.
- `autofix.app_id` in the config file must be the App's numeric id, and `/sentinel/github-app-private-key` must be one of that App's active private keys.

## The routine's environment must reach GitHub

The fix phase fetches the base branch, pushes a branch, and calls the pull-request API, all against GitHub, from inside the routine's cloud environment. That environment's egress policy has to permit reaching those endpoints or the fix phase cannot run at all. Investigation is unaffected either way, so the symptom is narrow and uniform: findings keep arriving and threads keep getting their replies, while every grant fails and no pull request ever opens. Read that pattern as an egress question before a code question.

It is worth stating what the two phases need separately, because they are not the same. Investigation reads the repository at the release SHA, which the routine's own environment provides for the repository it is bound to. The fix phase additionally writes: it pushes to a branch and creates a pull request through the API. Widen the policy by exactly the endpoints that needs, rather than opening it generally. The narrower the policy stays, the more the out-of-band destination check in [the security model](/sentinel/security-model/) is actually worth.

## Runbook: rotating the GitHub App private key

1. Generate a second private key in the GitHub App settings. GitHub Apps allow two active keys at once, so this rotation is zero-downtime: the old key keeps authenticating while the new one rolls out.
2. Update the key in both places it lives. Set `AWS_REGION` to the region you deployed
   into first; `scripts/put-parameters.sh` and the receiver both default to `us-east-1`,
   but nothing requires it.
   - **Your password manager:** update the stored copy manually.
   - **SSM parameter** (read by the receiver at cold start). `scripts/put-parameters.sh` writes all five receiver secrets together and its `put()` helper hard-exits the moment any of them is unset, so it is not a safe tool for rotating this one key alone unless you also have the other four ready to supply in the same run. Update the parameter directly instead:
     ```bash
     aws ssm put-parameter \
       --name /sentinel/github-app-private-key \
       --type SecureString \
       --value "$GITHUB_APP_PRIVATE_KEY" \
       --overwrite \
       --region "$AWS_REGION"
     ```
3. Confirm the new key is actually the one in place, not just that GitHub still accepts requests. Both keys stay valid until you delete one, so a successful mint proves nothing about which key produced it:
   - SSM: `aws ssm get-parameter --name /sentinel/github-app-private-key --with-decryption --region "$AWS_REGION" --query Parameter.Value --output text`, and diff the output against the new key file.
   - The receiver caches its App client per container, so a warm Lambda keeps using the key it read at cold start. Wait for a cold start, or force one with a no-op config deploy, before reading anything into the next autofix outcome.
4. Only once both checks in step 3 pass, delete the old key from the App settings.

## The disclosure gates

Three gates decide what this repository is willing to hand a stranger, and they cover different things.

`tests/test_public_tree.py` bans specific strings, and gitleaks (`secret-scan.yml`) matches credential shapes. Both catch what someone already thought to describe, both are deterministic, and both run locally before anything is pushed for any clone that ran `pre-commit install` (see [CONTRIBUTING.md](https://github.com/sentasity/sentinel/blob/main/CONTRIBUTING.md)). On a public repository every pushed branch is published, so that local hook is the only gate that fires before content becomes public; CI is the backstop for clones without it.

The third gate reads. CodeRabbit reviews every pull request against the disclosure rules in [`.coderabbit.yaml`](https://github.com/sentasity/sentinel/blob/main/.coderabbit.yaml), which tell it to flag anything naming another repository's internals, a real organization or account identifier, a live endpoint, or a measurement taken against a live system, and to cite a file and line without ever quoting the value it is flagging. It also reports ordinary security weaknesses in the change, such as a credential reaching a step that does not need it.

It blocks the merge until its comments are resolved. That is deliberate, and it is the lesson of what it replaced: a dedicated scanning workflow that reported a passing check while leaving major findings underneath as annotations, which went unread. Resolving a false positive is a click, and a model reviewing prose for disclosure will produce some. An unread finding costs whatever it was warning about.

That workflow also had to hold a Claude subscription credential as a repository secret to do its reading, which put a long-lived personal credential somewhere every repository administrator could reach. Retiring it removed the last one.

**What was lost.** The old scan could sweep the whole tracked tree on demand, not just a diff. CodeRabbit reviews changes, so untouched files are no longer re-read on a schedule, and the `path_filters` in [`.coderabbit.yaml`](https://github.com/sentasity/sentinel/blob/main/.coderabbit.yaml) exclude generated trees (`fixtures/`, `docs/brand/assets/`) from review entirely. Those are covered by their generators and by `tests/test_public_tree.py`, which still reads every tracked file for banned strings. So the accurate claim is narrower than "everything gets read": the tree was swept clean before the change, and every hand-written change outside those filters passes a reader on the way in.

The banned strings themselves are split in two. Generic shapes live in the test file; the literals that identify a real deployment live in an untracked local file, `config/banned.local.txt`, because a tracked ban list is an index of everything it protects. CI materializes that file from the `SENTINEL_BANNED_PATTERNS` secret and sets `SENTINEL_REQUIRE_BANNED_LOCAL`, so a vanished secret fails the suite rather than quietly narrowing the scan. After editing the local file, mirror it back:

```bash
gh secret set SENTINEL_BANNED_PATTERNS < config/banned.local.txt
```

A fork's pull request runs without the secret and tests the generic patterns only, which is the same posture a stranger's clone gets: the push to the default branch after the merge is where the full list applies.

**Accepted disclosures** live in [`.github/disclosure-allowlist.md`](https://github.com/sentasity/sentinel/blob/main/.github/disclosure-allowlist.md). Adding an entry changes what a public repository is willing to expose, so it gets reviewed like any other change.

## Reading autofix in the logs

These are the four markers to filter on. They cover the gate's decisions and every outcome that reaches a thread, but they are not everything autofix logs: see the unmarked lines below the table.

| Marker | Means |
|---|---|
| `AUTOFIX_DECLINED` | The gate said no, with the reason on the same line. Not a fault: this is the normal outcome for most findings |
| `AUTOFIX_DISPATCHED` | A grant was staged, with its dispatch id. Staging happens before the batch's token is minted, so a withdrawal line can still follow |
| `AUTOFIX_FAILED` | Something went wrong: a mint failure, a crashed gate, a session reporting `failed`, or a callback deadline passing with nothing reported |
| `AUTOFIX_UNVERIFIED` | A session reported a pull request the receiver could not confirm the App authored. Always accompanied by `AUTOFIX_FAILED`, which follows it on the same line |

### The lines that carry no marker

A filter built from the table above will miss several things, and one of them matters operationally. **Rejections at `/autofix-result` are unmarked warnings**: a request with no usable bearer token, one naming an unknown dispatch or presenting the wrong token, and one carrying a status outside the accepted set each log a plain `rejected autofix callback ...` warning. So repeated authentication failures against the callback endpoint, which is the shape a probe of that endpoint would take, produce nothing any of the four markers would catch. Search the callback route's own wording, not the markers, when that is the question.

Also unmarked: a callback arriving for a dispatch the sweep already settled logs an `already settled; ignoring` notice at info, which is normal and means the deadline won a race. And a completion reply that cannot be posted to the thread carries the receiver's general delivery-failure marker rather than an autofix one, so a chat outage during an autofix reply is found under that marker. The App client's own failures log with their own wording too, each naming the underlying error. The token mint and the pull-request author fetch also name the repository they were working against; the App slug fetch does not, because the slug is a property of the App rather than of any one repository.

### `AUTOFIX_UNVERIFIED`: treat the pull request as untrusted

The receiver checks every reported pull request: the URL must parse, name the configured target repository, and resolve to a pull request whose author is the autofix App's own bot login. Anything else is unverified, and the thread gets a warning rather than a plain link.

The line names the short id and the URL that was reported. What to do:

1. **Treat the pull request as untrusted.** It was opened by something other than the App identity the pipeline is supposed to use, or in a repository other than the target, or by an identity the receiver could not read at all. Do not review it as a normal autofix pull request and do not merge it.
2. **Close it.** If a fix is genuinely wanted, it should come back through the pipeline or be written by hand, not merged on the strength of a claim the receiver rejected.
3. **Read the session transcript.** This is the part that matters, because the marker tells you the pipeline caught something without telling you what. The transcript shows which credential the session actually used and, if the pull request was opened under a person's identity, that a connector was used where the vended token was meant to be.
4. **Rule out the boring causes before the alarming one.** A GitHub outage during the author lookup, or an App whose slug could not be fetched, both fail closed and report unverified. Those are noise; a pull request genuinely authored by someone else is not.

The line carries `AUTOFIX_FAILED` too, so the alarm on that marker fires for this case as well and it does not need an alarm of its own.

### `AUTOFIX_FAILED ... token mint failed`

Minting is the one step between a passing gate and a session that can act. When it fails, every grant staged for that batch is withdrawn: the dispatch records settle as failed, and each thread's reply line reads `Autofix declined: could not mint a GitHub credential.` rather than promising a fix that has no credential to start with. The findings replies themselves are unaffected, which is the design: autofix failing must never cost a thread its investigation.

One line per withdrawn grant appears in the log, each naming the short id. The mint failure's own cause is logged separately by the App client, naming the repository and the underlying error. Work through the App checklist above: the wrong `autofix.app_id`, a private key that no longer matches an active key, or an App not installed on the target repository all land here.

If a batch instead reports a crash before minting was attempted, the cause is usually the App private key parameter being unreadable at cold start rather than GitHub itself.

## Runbook: replaying an alert the receiver has already seen

Sentry will not re-send an alert for a known issue. New-issue rules fire on `first_seen` only, and a repeat event on an unchanged release finds the investigation row and stops before any Sentry call. So when you need the receiver to process a known issue again, after fixing something in the pipeline for example, sign a webhook body and post it yourself:

```bash
python -m scripts.replay_alert --issue 1000000007 --environment prod --dry-run
```

The body is `fixtures/sentry-webhook-alert.json` with the target issue's fields written over it from its stored `alert:<environment>` row, so you can only replay an issue the receiver has already posted. The signature comes from `receiver.handler.sign_body`, the same function `/sentry` verifies against, and the webhook secret is read from SSM rather than the environment so it never lands in shell history.

Start with `--dry-run`. It prints the exact body and target and sends nothing. A live replay posts a real card to that environment's real Teams channel.

Two rows make a replay a no-op for a repeat, and `--reset` deletes both before posting:

- `investigation:<env>#<release>` stops the enqueue, so no session fires and no findings arrive.
- `autofix:<env>#<release>` stops the autofix gate one stage later, as "already attempted for this release".

Each delete is conditional on the row existing, and the script prints `deleted:` or `absent:` per row. That distinction is the point: an unconditional `delete-item` against a mistyped sort key succeeds silently and reads as a successful clear. The `alert:<environment>` row is never touched, because it is the replay's own input.

Without `--reset`, a repeat issue posts a fresh card and nothing else happens. That is the right mode for a freshly staged error that has no rows yet.

## Configuration probe

The prompts in `prompts/` are templates. `REPLACE_WITH_FUNCTION_URL` stands in
for the receiver's Function URL and must be substituted with the real origin
when the prompt is pasted into the routine. The session cross-checks that
origin against the `SENTINEL_RECEIVER_URL` environment variable, so a prompt
pasted with the placeholder left in place fails the check and posts nothing.

The routines API exposes no configuration read, so the routine's repository binding and connector set can only be verified by firing a session that reports on itself (`prompts/probe.md`, reporting to `/findings/probe`; `scripts/probe_routine.py` fires it). Connector drift is not detected automatically: re-run the probe whenever the routine or the account's connectors change.

**Give the probe its own routine.** A routine holds one prompt at a time, so a single routine cannot be both. Create a second routine carrying `prompts/probe.md` and leave the first on `prompts/investigator.md`. Record the probe's id as `trigger.probe_routine_id` and put its trigger token in the parameter store under `trigger.probe_token_ref`, then:

```bash
scripts/probe_routine.py
```

Read the session transcript alongside the receiver's log group for the `/findings/probe` POST. The probe's pass condition is agreement between the two: a POST with no matching transcript proves nothing, which is why `handle_probe` can be unauthenticated.

**A trigger token authorises exactly one routine.** The investigator's token cannot fire the probe, and the API answers with `401 Token is not authorized for this routine`, which names the routine and so reads like a wrong id when the id is fine. Each routine needs its own token recorded separately.

**Running one routine instead of two costs you a swap, and the restore is the part that bites.** If you have not created a probe routine, probing means replacing the investigator's prompt with `prompts/probe.md`, firing `ROUTINE_ID=... ROUTINE_TRIGGER_TOKEN=... scripts/probe_routine.py`, reading the result, and then putting `prompts/investigator.md` back. Until you restore it, every live alert fires a probe session instead of an investigation, and those alerts get the deadline sweep's "did not report back" reply rather than findings. A second routine removes that window entirely, which is why it is the recommended shape.

Firing the investigator's own routine with this script does *not* run a probe. The script sends `{"probe": true}`, the investigator sees a payload missing all five required fields (`project`, `issue_ids`, `release`, `batch_id`, `reply_token`), and correctly refuses to interpret it, reporting a malformed fire instead. That is the investigator behaving as designed, not a probe result.

A malformed-fire report is still useful even though it is not a probe. It confirms the receiver URL the routine actually holds, that egress reaches that host, and that `/findings` rejects an unauthenticated POST, without touching the prompt at all. When all you need is "does the routine still point at the right receiver", fire the script and read the report rather than doing the swap.

## Falling back to stock Sentry alerts

To fall back to Sentry's stock Teams cards without touching AWS at all, run `scripts/migrate_rules.py rollback` (see [Sentry setup](/sentinel/deploy/sentry/)). The alert table is retained on stack delete, so `cdk destroy` leaves posted-message history intact.
