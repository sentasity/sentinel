Runbooks for the credentials the engine holds, what the Sentinel App needs on the GitHub side, switching issue filing on, and how to read what the pipeline reports about itself. Deploying the receiver itself is covered in [infra/README.md](https://github.com/sentasity/sentinel/blob/main/infra/README.md); the one-time Microsoft and Sentry setup lives in [Microsoft setup](/sentinel/deploy/microsoft/) and [Sentry setup](/sentinel/deploy/sentry/).

## Credential inventory

| Credential | Where it lives | Purpose |
|---|---|---|
| `/sentinel/github-app-private-key` | SSM SecureString, receiver | The Sentinel App's private key, read by the receiver at cold start; it mints the scoped installation token the receiver uses to open each pull request and to make each issue write |
| `SENTRY_WEBHOOK_SECRET`, `SENTRY_API_TOKEN`, `BOT_CLIENT_SECRET`, `ROUTINE_TRIGGER_TOKEN` | SSM SecureStrings, receiver | Webhook verification, Sentry API access, the bot identity, and the routine fire token |
| Installation tokens | Nowhere: minted per pull request or per issue operation inside the receiver, spent in the same invocation, never returned or stored | Lets the receiver push one branch and open one pull request (`contents: write` and `pull_requests: write`), or make one issue operation's write, downscoped to that operation (`OP_PERMISSIONS`); scoped to the target repo, one hour |
| Callback capability tokens | DynamoDB, hashed, one per dispatch | Bearer credential the fix session presents to `/autofix-result`; scoped to a single dispatch, not reusable |
| Tracking tokens | DynamoDB, hashed, one per delivered result while issue filing is on for its environment | Bearer credential a session presents to `/issues`; scoped to one alert and its thread, dead at its grant's `expires_at` (30 minutes after findings, or 90 when the result also earned an autofix grant) |
| `SENTINEL_BANNED_PATTERNS` | Actions secret, engine repo | The deployment-identifying ban patterns `tests/test_public_tree.py` enforces; not a credential, but held like one because publishing the list would index what it protects |

The routine trigger token is never stored in this repo; keep the only other copy in your password manager.

## What the Sentinel App needs

The receiver mints every GitHub credential itself, for autofix pull requests and for issue writes alike, so the App's configuration is the only thing standing between a passing gate and a pull request, or between a session's issue operation and the repository:

- The App must be **installed on the target repository**, the one named by `target_repo`. Minting looks that installation up by repository, so an App installed on the organization but not on this repository fails at the lookup.
- For autofix, the installation must grant **contents: write** and **pull requests: write**. The receiver downscopes each fix's token to exactly those two, and a token can never hold a permission the installation lacks, so a missing one produces a token that cannot push or cannot open the pull request.
- For issue filing, the installation must also grant **Issues: read and write** (create, comment, reopen, labels, the issue type on create, and issue-field values), organization **Projects: read and write** (adding a new issue to the board `issues.project_number` names), and organization **Issue fields: read-only** (the field and option names `set_fields` resolves). Each issue operation mints its own token, downscoped to what that operation needs (`OP_PERMISSIONS` in `receiver/github_app.py`), and none carries contents, pull requests, workflows or administration. Organization permissions reach every board in the organization; the named operations are what confine the App's board writes to the one configured.
- GitHub holds a permission change until an **organization owner accepts it** on the installation. Until then the installation keeps its old permissions, autofix is unaffected, and every issue operation fails at the mint with a 502.
- Do **not** grant `workflows`. It is excluded from every minted token on purpose ([why](/sentinel/security-model/)), and granting it at the installation widens the App's own reach for no benefit here.
- `autofix.app_id` in the config file must be the App's numeric id, and `/sentinel/github-app-private-key` must be one of that App's active private keys. Issue filing uses the same App and key, even with autofix off.

## The routine's environment reaches GitHub for reads only

The fix phase fetches the base branch and nothing else from GitHub: the session sends its
changed files to the receiver, and the receiver opens the pull request. So the routine's
environment needs the same GitHub reach the investigation already has, the repository
fetch, and no more. If fixes are failing while findings keep arriving, the pattern points
at the receiver's side, the App configuration above or the `AUTOFIX_FAILED` lines below,
before it points at egress.

## Runbook: rotating the GitHub App private key

1. Generate a second private key in the GitHub App settings. GitHub Apps allow two active keys at once, so this rotation is zero-downtime: the old key keeps authenticating while the new one rolls out.
2. Update the key in both places it lives. Set `AWS_REGION` to the region you deployed
   into first; `scripts/put-parameters.sh` and the receiver both default to `us-east-1`,
   but nothing requires it.
   - **Your password manager:** update the stored copy manually.
   - **SSM parameter** (read by the receiver at cold start). `scripts/put-parameters.sh` writes all five receiver secrets together and its `put()` helper hard-exits the moment any of them is unset, so it is not a safe tool for rotating this one key alone unless you also have the other four ready to supply in the same run. Update the parameter directly instead:
     ```bash
     aws ssm put-parameter \
       --name /sentinel/github-app-private-key \
       --type SecureString \
       --value "$GITHUB_APP_PRIVATE_KEY" \
       --overwrite \
       --region "$AWS_REGION"
     ```
3. Confirm the new key is actually the one in place, not just that GitHub still accepts requests. Both keys stay valid until you delete one, so a successful mint proves nothing about which key produced it:
   - SSM: `aws ssm get-parameter --name /sentinel/github-app-private-key --with-decryption --region "$AWS_REGION" --query Parameter.Value --output text`, and diff the output against the new key file.
   - The receiver caches its App client per container, so a warm Lambda keeps using the key it read at cold start. Wait for a cold start, or force one with a no-op config deploy, before reading anything into the next autofix outcome.
4. Only once both checks in step 3 pass, delete the old key from the App settings.

## The disclosure gates

Three gates decide what this repository is willing to hand a stranger, and they cover different things.

`tests/test_public_tree.py` bans specific strings, and gitleaks (`secret-scan.yml`) matches credential shapes. Both catch what someone already thought to describe, both are deterministic, and both run locally before anything is pushed for any clone that ran `pre-commit install` (see [CONTRIBUTING.md](https://github.com/sentasity/sentinel/blob/main/CONTRIBUTING.md)). On a public repository every pushed branch is published, so that local hook is the only gate that fires before content becomes public; CI is the backstop for clones without it.

The third gate reads. CodeRabbit reviews every pull request against the disclosure rules in [`.coderabbit.yaml`](https://github.com/sentasity/sentinel/blob/main/.coderabbit.yaml), which tell it to flag anything naming another repository's internals, a real organization or account identifier, a live endpoint, or a measurement taken against a live system, and to cite a file and line without ever quoting the value it is flagging. It also reports ordinary security weaknesses in the change, such as a credential reaching a step that does not need it.

It blocks the merge until its comments are resolved. That is deliberate, and it is the lesson of what it replaced: a dedicated scanning workflow that reported a passing check while leaving major findings underneath as annotations, which went unread. Resolving a false positive is a click, and a model reviewing prose for disclosure will produce some. An unread finding costs whatever it was warning about.

That workflow also had to hold a Claude subscription credential as a repository secret to do its reading, which put a long-lived personal credential somewhere every repository administrator could reach. Retiring it removed the last one.

**What was lost.** The old scan could sweep the whole tracked tree on demand, not just a diff. CodeRabbit reviews changes, so untouched files are no longer re-read on a schedule, and the `path_filters` in [`.coderabbit.yaml`](https://github.com/sentasity/sentinel/blob/main/.coderabbit.yaml) exclude generated trees (`fixtures/`, `docs/brand/assets/`) from review entirely. Those are covered by their generators and by `tests/test_public_tree.py`, which still reads every tracked file for banned strings. So the accurate claim is narrower than "everything gets read": the tree was swept clean before the change, and every hand-written change outside those filters passes a reader on the way in.

The banned strings themselves are split in two. Generic shapes live in the test file; the literals that identify a real deployment live in an untracked local file, `config/banned.local.txt`, because a tracked ban list is an index of everything it protects. CI materializes that file from the `SENTINEL_BANNED_PATTERNS` secret and sets `SENTINEL_REQUIRE_BANNED_LOCAL`, so a vanished secret fails the suite rather than quietly narrowing the scan. After editing the local file, mirror it back:

```bash
gh secret set SENTINEL_BANNED_PATTERNS < config/banned.local.txt
```

A fork's pull request runs without the secret and tests the generic patterns only, which is the same posture a stranger's clone gets: the push to the default branch after the merge is where the full list applies.

**Accepted disclosures** live in [`.github/disclosure-allowlist.md`](https://github.com/sentasity/sentinel/blob/main/.github/disclosure-allowlist.md). Adding an entry changes what a public repository is willing to expose, so it gets reviewed like any other change.

## Reading autofix in the logs

These are the three markers to filter on. They cover the gate's decisions and every outcome that reaches a thread, but they are not everything autofix logs: see the unmarked lines below the table.

| Marker | Means |
|---|---|
| `AUTOFIX_DECLINED` | The gate said no, with the reason on the same line. Not a fault: this is the normal outcome for most findings |
| `AUTOFIX_DISPATCHED` | A grant was staged, with its dispatch id |
| `AUTOFIX_FAILED` | Something went wrong: a crashed gate, a session reporting `failed`, a `fix_ready` payload that broke a rule, a pull request the receiver could not open, or a deadline passing with nothing settled. The rest of the line says which |

### The lines that carry no marker

A filter built from the table above will miss several things, and one of them matters operationally. **Rejections at `/autofix-result` are unmarked warnings**: a request with no usable bearer token, one naming an unknown dispatch or presenting the wrong token, and one carrying a status outside the accepted set each log a plain `rejected autofix callback ...` warning. So repeated authentication failures against the callback endpoint, which is the shape a probe of that endpoint would take, produce nothing any of the four markers would catch. Search the callback route's own wording, not the markers, when that is the question.

Also unmarked: a callback arriving for a dispatch the sweep already settled logs an `already settled; ignoring` notice at info, which is normal and means the deadline won a race. And a completion reply that cannot be posted to the thread carries the receiver's general delivery-failure marker rather than an autofix one, so a chat outage during an autofix reply is found under that marker. The App client's own failures log with their own wording too, each naming the underlying error. The App client's token mint and pull-request sequence both name the repository they were working against.

### `AUTOFIX_FAILED ... session reported failure`

The session stopped the grant itself and reported `failed`. That callback carries no reason, so the line ends there, and the reason lives only in the session's transcript: find the routine run that started just before the matching `AUTOFIX_DISPATCHED` line and read how its fix phase ended.

The usual cause is step 7d's test. The session wrote a fix but could not run its test, either because the routine's environment lacks a dependency or because the session never found where the environment installed it. The first needs the environment's setup script fixed. The second is what the prompt's instruction to search for installed dependencies covers, so a transcript showing a session that gave up without searching is a reason to make the environment put its dependencies where a session looks first, such as on `PATH`. Once the cause is fixed, replay the alert with `--reset` (see the replay runbook below) to get the pull request.

### `AUTOFIX_FAILED ... rejected fix payload`

The session sent a `fix_ready` body that broke one of the receiver's rules, and the line names the rule: both or neither of `files` and `patch`, a path under `.github/` or matching `autofix.exclude_paths` (on either side of a rename), a path that is not plain and repository-relative, more than twenty files, a symlink or submodule mode, more than 512 KB of whole-file content or a patch over 4 MB, a patch that is not plain `git diff` output (the line says where it stopped reading), a title that is empty or wraps, or a base commit that is not a full SHA. The record is settled as failed, the thread has been told, and no GitHub call was made.

The one worth acting on is a path rejection, because it means the session decided a fix needed a file the operator ruled out. Read the transcript to see whether the exclusion is right or the finding was steered; either way the pull request did not happen, which is the design.

### `AUTOFIX_FAILED ... at base_sha`

The payload passed and the record was claimed, but the base tree refused the fix, and the line names the file and the reason. It is the session's fix that is wrong here, not the GitHub App, so nothing on the App checklist applies:

- `differs at base_sha from the version the patch was made against`, `does not match base_sha at line N`, or `does not reproduce blob ...`: the patch was not taken against the base commit it names. The session diffed against some other commit, or edited the patch by hand. The receiver applies hunks only where they say and checks every result against git's own blob id, so this never lands as a near miss.
- `does not exist at base_sha` or `already exists at base_sha`: the same mismatch, seen as a path the patch edits that is not there, or creates that already is.
- `is a symlink at base_sha`, `is a submodule at base_sha`, `is a directory at base_sha`, or `runs through ... which is not a directory`: the fix would replace or write through something that is not a regular file. A pure rename carries no mode in a patch, so only the base tree can catch it.
- `more than the ... bytes the receiver rewrites`: the files the patch modifies are larger in total than the receiver will read and upload in one invocation. GitHub builds blobs only from whole content, so a small change to a large file still costs the file's full size here.

No branch was created for any of these. The session's response carried the same reason, and the transcript shows how it made the patch.

### `AUTOFIX_FAILED ... pull request not opened`

The payload passed, the record was claimed, and one of the GitHub calls that build the branch and open the pull request did not succeed. The App client's own line, just above, names the failing call and the underlying error. Work through the App checklist above: the wrong `autofix.app_id`, a private key that no longer matches an active key, an App not installed on the target repository, or an installation missing one of the two permissions all land here. A branch that already exists (a replayed dispatch id) lands here too, as does a base commit that is not on the base branch (the session checked out something other than the branch it was told to; the App client's line says so) and a sequence that ran out of its time budget.

A failure after the branch was created leaves that branch behind with no pull request on it. It is inert, and its name carries the dispatch id that failed:

```bash
git ls-remote --heads origin 'autofix/*'
```

lists them, and once you have confirmed no pull request references a branch, `git push origin --delete <branch>` removes it. The receiver never deletes branches itself; that is a destructive path it does not need.

### `AUTOFIX_FAILED ... opening timeout`

The receiver claimed a record and never settled it, which means the invocation died between its first GitHub call and its last. The sweep fails the record after three minutes and the thread reads that the receiver did not finish opening the pull request. Check the receiver's own error log for the invocation, then the branch listing above, since the branch may exist without its pull request.

If a batch instead reports a crash before any of this, the cause is usually the App private key parameter being unreadable at cold start rather than GitHub itself.

## Reading issue tracking in the logs

Issue filing logs one marker, `ISSUE_TRACKING_FAILED`, and the `IssueTrackingFailures` alarm fires on a single line of it in five minutes. The rest of the line names the alert and the case:

| Line | Means |
|---|---|
| `... <short id> grant not written: <error>` | The receiver could not write a tracking grant while delivering findings. The findings reply still posted, but the session got no grant for that result, so nothing can file it |
| `... <short id> issue op rejected: <rule>` | A session sent an operation that broke one of the proxy's rules, named on the line. Like `FINDINGS_REJECTED`, it means the prompt and the receiver disagree |
| `... <short id> <op> failed: <step>` | A GitHub call did not succeed, and the step says which: `token mint failed`, `read the issue`, `list the labels`, `create the issue`, `post the comment`, `reopen the issue`, `read the issue fields`, `field <name> is not single-select` (a configured field of another type), `set the field values`, `read the field values back`, `field values did not persist`, `read the project`, or `add the issue to the project`. The session may retry once |
| `... <short id> <op> rejected: <reason>` | GitHub refused the request and wrote nothing (`GitHub refused the issue as sent`, usually an issue type it does not recognize), or `set_fields` named an option no field offers |
| `... <short id> <op> #<n> landed with warnings: <what>` | The write happened, but a label or the type is not on the issue as sent: a label the repository does not define, dropped before sending, or one GitHub dropped on its own |
| `... <short id> <op> crashed: <error>` | The receiver raised mid-operation. The operation's record is failed and the alert's tracking claim released, so a retry can run |
| `... <short id> <op> landed on #<n> after the grant closed` | An operation finished just after the backstop expired its grant. The issue exists, and the thread got its link after the backstop's notice |
| `... <short id> left untracked at grant expiry` | The backstop: the grant expired with no issue filed, commented on or reopened |
| `... <short id> may not have finished filing at grant expiry` | The backstop found an operation that claimed the alert and never settled, so an issue may exist |

**Refusals carry no marker.** A well-formed operation that a cap or a state forbids is answered 409 and logged at warning as `issue op for <short id> refused: <reason>`: a per-alert or daily cap reached, the alert already tracked, an issue that is not in the target repository or is a pull request, a reopen of an open issue, an operation still in progress, or an environment no longer in `issues.environments`. If a refusal leaves the alert untracked, the backstop logs the marker once, when the grant expires. Authentication failures at `/issues` are plain `rejected issue op ...` warnings, the same shape as the callback route's.

**The two backstop notices** are what the alert's thread reads when its grant expires with nothing tracked: `No GitHub issue was filed for this alert, so it is tracked only in this thread.`, or, when an operation died mid-filing, `Sentinel may not have finished filing this alert in GitHub; check the repository for an issue before filing one.` Either is followed by the search-unavailable line when the session's duplicate search had failed. A grant whose result opened a pull request, or whose fix attempt failed on the receiver's side, is released without a notice: the pull request, or the `AUTOFIX_FAILED` line and its own thread reply, already says what happened.

A thread reply or a notice that cannot be posted carries the receiver's general delivery-failure marker (`issue tracking reply for ...`, `tracking notice for ...`), not this one. A grant with no thread to reply in (its alert card never posted) skips the reply with a plain `no thread to reply in for ...` warning.

## Runbook: replaying an alert the receiver has already seen

A repeat alert on an unchanged release finds the investigation row and stops before any Sentry call: it posts a pointer to the earlier thread, or retries once if that attempt failed, and never re-runs a delivered investigation. Which repeats arrive at all depends on the alert rules you configured: a new-issue rule fires once per issue per environment, while frequency, regression, and reappearance rules re-fire for a known issue. So when you need the receiver to process a known issue again, after fixing something in the pipeline for example, sign a webhook body and post it yourself:

```bash
python -m scripts.replay_alert --issue 1000000007 --environment prod --dry-run
```

The body is `fixtures/sentry-webhook-alert.json` with the target issue's fields written over it from its stored `alert:<environment>` row, so you can only replay an issue the receiver has already posted. The signature comes from `receiver.handler.sign_body`, the same function `/sentry` verifies against, and the webhook secret is read from SSM rather than the environment so it never lands in shell history.

Start with `--dry-run`. It prints the exact body and target and sends nothing. A live replay posts a real card to that environment's real Teams channel.

Two rows make a replay a no-op for a repeat, and `--reset` deletes both before posting:

- `investigation:<env>#<release>` stops the enqueue, so no session fires and no findings arrive.
- `autofix:<env>#<release>` stops the autofix gate one stage later, as "already attempted for this release".

Each delete is conditional on the row existing, and the script prints `deleted:` or `absent:` per row. That distinction is the point: an unconditional `delete-item` against a mistyped sort key succeeds silently and reads as a successful clear. The `alert:<environment>` row is never touched, because it is the replay's own input.

Without `--reset`, a repeat issue posts a fresh card that points at the earlier thread, or retries a failed investigation if its retry budget is unspent. That is the right mode for a freshly staged error that has no rows yet.

## Runbook: updating the investigator's stored prompt

A routine holds one prompt, and the receiver's contract with it changes whenever step 7 of `prompts/investigator.md` does. The public routines API cannot read or write a routine's configuration, so the update happens on the routine's own page at claude.ai: substitute the receiver's origin for `REPLACE_WITH_FUNCTION_URL` in the repository file, paste the result into the routine's prompt, save, then reopen the routine and compare its prompt against the substituted file. A Claude Code session with routine tooling can make the same edit and read it back, which is how the comparison is automated when one is at hand. Either way, a prompt that differs from the file is a partial update. The probe routine keeps its own prompt and is not touched by this.

After an update, a `FINDINGS_SCHEMA_OUTDATED schema_version <n>` warning in the receiver's log group means a session posted findings in a schema older than the one `prompts/investigator.md` emits, so it ran an older prompt. The receiver delivers those findings as usual, without an urgency line on the reply card, so nothing is lost, and the marker is counted rather than alarmed. It is expected only for sessions that were already running when the prompt was swapped. Once those have finished, a new one means the routine still holds an older prompt: compare its prompt against the substituted file again.

## Configuration probe

The prompts in `prompts/` are templates. `REPLACE_WITH_FUNCTION_URL` stands in
for the receiver's Function URL and must be substituted with the real origin
when the prompt is written to the routine. The session cross-checks that
origin against the `SENTINEL_RECEIVER_URL` environment variable, so a prompt
written with the placeholder left in place fails the check and posts nothing.

The routines API exposes no configuration read, so the routine's repository binding and connector set can only be verified by firing a session that reports on itself (`prompts/probe.md`, reporting to `/findings/probe`; `scripts/probe_routine.py` fires it). Connector drift is not detected automatically: re-run the probe whenever the routine or the account's connectors change.

**Give the probe its own routine.** A routine holds one prompt at a time, so a single routine cannot be both. Create a second routine carrying `prompts/probe.md` and leave the first on `prompts/investigator.md`. Record the probe's id as `trigger.probe_routine_id` and put its trigger token in the parameter store under the key `trigger.probe_token_ref` names (`probe-trigger-token` by default; the config holds the key name, never the token), then:

```bash
scripts/probe_routine.py
```

Read the session transcript alongside the receiver's log group for the `/findings/probe` POST. The probe's pass condition is agreement between the two: a POST with no matching transcript proves nothing, which is why `handle_probe` can be unauthenticated.

**A trigger token authorises exactly one routine.** The investigator's token cannot fire the probe, and the API answers with `401 Token is not authorized for this routine`, which names the routine and so reads like a wrong id when the id is fine. Each routine needs its own token recorded separately.

**Running one routine instead of two costs you a swap, and the restore is the part that bites.** If you have not created a probe routine, probing means replacing the investigator's prompt with `prompts/probe.md`, firing `ROUTINE_ID=... ROUTINE_TRIGGER_TOKEN=... scripts/probe_routine.py`, reading the result, and then putting `prompts/investigator.md` back. Until you restore it, every live alert fires a probe session instead of an investigation, and those alerts get the deadline sweep's "did not report back" reply rather than findings. A second routine removes that window entirely, which is why it is the recommended shape.

Firing the investigator's own routine with this script does *not* run a probe. The script sends `{"probe": true}`, the investigator sees a payload missing all five required fields (`project`, `issue_ids`, `release`, `batch_id`, `reply_token`), and correctly refuses to interpret it, reporting a malformed fire instead. That is the investigator behaving as designed, not a probe result.

A malformed-fire report is still useful even though it is not a probe. It confirms the receiver URL the routine actually holds, that egress reaches that host, and that `/findings` rejects an unauthenticated POST, without touching the prompt at all. When all you need is "does the routine still point at the right receiver", fire the script and read the report rather than doing the swap.

## Runbook: enabling issue filing

Issue filing ships off, and merging the engine change that carries it activates nothing: the receiver runs only what `cdk deploy` ships, the routine runs only the prompt pasted into it, and `issues.enabled: false` keeps the `/issues` route answering 404 and every findings response's `tracking` null. Switching it on is a sequence of operator steps, each checked before the next:

1. **Deploy the receiver with the flag still off.** The receiver must accept findings schema v3 before the routine sends it, or every v3 findings POST is rejected and each thread gets the deadline reply instead of its findings. Check: `/health` answers `ok`, and the next findings delivery posts as before with no `FINDINGS_REJECTED` line.
2. **Update the App's permissions** as [What the Sentinel App needs](#what-the-sentinel-app-needs) lists, and have an organization owner accept the request. This step is independent of the others and can run any time before step 4. Check: the installation page lists the new permissions with no pending request.
3. **Update the investigator routine.** Set `issues.conventions` first, because the paste writes those paths into the prompt, and confirm each path exists on every branch your releases are cut from. Then follow updating the investigator routine, and re-run the configuration probe. Check: a replayed alert's findings card shows its urgency, and the receiver's log shows no request to `/issues`, which proves the issue step stays dormant while the flag is off.
4. **Turn filing on for one environment.** Set `issues.enabled: true`, `issues.environments` to that one environment, `issues.proxy_url`, and `issues.issue_types`, `issues.fields` and `issues.project_number` as the target repository uses them, then deploy with the same `cdk deploy`. `assert_ready` runs at synth, so a missing or placeholder value stops the deploy before anything ships. Check: replay alerts in that environment until each path has happened once (a new issue, a comment on an open duplicate, a reopen of a closed one, a new issue linked to a related one, and a create with the duplicate search unavailable), and read each issue and each thread reply. If any path fails, set the flag back off, fix, and re-run it and every path after it.
5. **Soak, then widen.** Leave it on for the first environment until several organic outcomes have been read end to end, then add the remaining environments to `issues.environments` and deploy.

Rollback works stage by stage, and the order matters: the routine's prompt goes back before the receiver does.

| Undo | How | Notes |
|---|---|---|
| Filing | `issues.enabled: false`, or drop the environment from `issues.environments`, then `cdk deploy` | The durable stop. The route re-checks both on every call, so a session holding a grant is refused at once. Issues already filed stay; close a misfiled one by hand as a duplicate or not planned |
| Emergency stop | Remove Issues write from the App's permissions | Takes effect at once with no approval and stops every issue write at the token mint, without touching autofix. Restore it once the flag is off |
| Emergency stop | Revert the routine's prompt | Stops new sessions from running the issue step at all |
| The routine | Paste the previous engine commit's substituted prompt, read it back, record it | Do this before rolling the receiver back |
| The receiver | Check out the previous engine commit and `cdk deploy` | Only while the routine runs the previous prompt: a routine still sending schema v3 gets every findings POST rejected |
| The App's permissions | Remove Issues write, Projects write and Issue fields read | Only after the flag is off, or live operations fail at the mint |

The receiver cannot delete or close anything, so no rollback touches an issue already filed: each one describes a real error.

## Falling back to stock Sentry alerts

To fall back to Sentry's stock Teams cards without touching AWS at all, run `scripts/migrate_rules.py rollback` (see [Sentry setup](/sentinel/deploy/sentry/)). The alert table is retained on stack delete, so `cdk destroy` leaves posted-message history intact.
